MOTION AUDIT · DESIGN-MOTION-PRINCIPLES

mwa-landing — polish is real but uneven, and the two moments users actually touch skip motion entirely

Editorial marketing site for a 30-day nutrition/habit program (Fraunces + Inter, forest/gold/cream). One scroll-reveal primitive carries almost the entire page; the interactive quiz and FAQ — the only two places a visitor clicks something — currently snap.

What it is: React 18 + Vite 6 marketing landing page Stack: Tailwind v4, vanilla CSS keyframes, no animation library Weighting: Jakub → Jhey → Emil (forms, nav)
4 Critical 3 Important 6 Opportunities

OVERALL

The hero's staggered entrance and the count-up stats show real motion literacy — someone here understands sequencing and reduced-motion. But that same care didn't reach the page's two interactive moments: the mini-quiz's phase changes (question → email capture → result) and the FAQ accordion both snap instantly, and a carousel dot indicator quietly animates width every 5 seconds. Meanwhile a single Reveal component does duty for headings, paragraphs, cards, and pull-quotes alike, which reads as templated rather than composed. Net: passes the accessibility bar in spirit but not in code coverage, and the moments that most need a considered feel are the ones currently getting none.

CriticalJakub

Mobile carousel dots animate width, not a transform

WhatThe mobile pagination dots use transition-all duration-300 while toggling Tailwind's w-1.5 / w-5 — that's a layout-triggering width transition, repeating every 5 seconds for as long as the section is in view.

Why it mattersWidth/height animations force layout recalculation on every frame; unlike the progress bar three components away in the same codebase, this one will visibly jank on low-end phones, and it repeats indefinitely during autoplay rather than firing once.

Recommended motionKeep the dot's box a fixed size and animate an inner pill with transform: scaleX() + transform-origin: left, exactly the technique already used for the quiz progress bar two files away.

CriticalJakub

prefers-reduced-motion guard covers 3 classes, not the page

WhatThe only reduced-motion override in index.css targets .reveal, .hero-enter, .screen-in by name. Every Tailwind utility transition sitewide — header blur-in, CTA hover-lift, FAQ icon rotate, progress-bar scaleX, input focus colors, showcase tab/dot states — sits outside that list and keeps animating in full for users who've asked for less motion.

Why it mattersThis skill treats prefers-reduced-motion as mandatory, no exceptions. A hand-picked class list is a maintenance trap: every new transition anyone adds is unprotected by default instead of protected by default.

Recommended motionAdd a wildcard fallback guard (*, *::before, *::after { transition-duration: 0.01ms !important; animation-duration: 0.01ms !important; }) alongside the existing named rules, matching the pattern this very report's shell CSS uses for its own demo cards.

One Reveal treatment, used identically 28 times, on unrelated content

WhatThe same opacity 0→1 + translateY(20px)→0, 700ms, single easing curve wraps headings, body paragraphs, list items, a pull-quote, stat numbers, and card grids across all 11 sections — with only the stagger delay varying.

Why it mattersThis is the anti-checklist's "uniform fade-in on every element" pattern by the book: applying the same polish treatment regardless of what the content actually is reads as templated, and text-only elements (the pull-quote in Story.jsx, FAQ headings) delay reading for motion that isn't earning its keep.

Recommended motionLet headings/eyebrows appear instantly (no wrap), reserve the fuller enter recipe for one deliberate moment per section (the stat block, the pull-quote), and keep the lighter/faster version for routine list and card reveals.

Issues to address
ImportantJheyJakub

Autoplay carousel has no visible pause control

WhatThe feature showcase advances every 5 seconds. Pausing only happens via onMouseEnter (desktop hover) or an incidental swipe; there is no visible button or indicator that lets a touch/keyboard user stop the motion on purpose.

Why it mattersAuto-updating content that a user can't stop is exactly what pause controls exist for (WCAG 2.2.2). It's also a delight tax: the playful crossfade becomes friction the moment someone wants to linger on one screen and can't make it stay.

Recommended motionAdd a small visible pause/play toggle with a depleting progress ring showing time-to-next-advance — gives the autoplay a legible "you're in control of this" affordance instead of a silent timer.

Issues to address
CriticalEmilJakub

Quiz → capture-form → result: three phases, zero transitions

WhatThe quiz's three phases render via plain {fase === 'quiz' && (…)} {fase === 'captura' && (…)} {fase === 'resultado' && (…)} conditionals with no AnimatePresence-equivalent and no CSS transition — each phase pops in and the previous one disappears with no exit at all.

Why it mattersThis is the page's one actual form, and the highest-stakes moment in the whole funnel — the step where a visitor becomes a lead. Emil's forms/nav weighting exists precisely for moments like this: state changes here should feel considered, not instant.

Recommended motionUse a CSS-transition state class (mount → toggle .mounted) per phase so the swap is interruptible if the user moves fast — a quick fade + 8-10px translate, exit subtler than enter.
